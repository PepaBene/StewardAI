# StewardAI: agentic workflows, RAG and whole-app AI access

Research snapshot: 5 October 2026; **status refreshed 10 October 2026** after the public-disclosure, Morningstar, quant and news plans were implemented. Builds on [ai_research_thesis_improvement_plan.md](ai_research_thesis_improvement_plan.md) (grounded research, claim ledger, verifier, evals), which stays the quality spec. This plan answers a different question: **how the AI gets to all of the app's data, the wider world and the owner's portfolio, and which parts need RAG, which need agents.** It changes no code.

## Verdict

1. **Do not build "RAG over everything".** Almost all of the app's data is structured (about 150 tables: positions, prices, fundamentals, macro, ownership, insider filings, graph edges, risk). The model should reach it through typed read-only tools, not through embeddings. Embeddings are for the minority that is prose.
2. **Build one hybrid text-retrieval tool** (keyword + vector, fused) over the prose corpus: filings, IR releases, news, reports, theses, the owner's notes.
3. **Make the agent loop the backbone and give it more tools.** Chat already is one; research is still a fixed pipeline and should become a planned, multi-agent run in deep mode.
4. **Add event-driven agents** that react to alerts, news and earnings and leave proposals in an inbox. This matches the strategy (event-driven rotation priced for risk) better than a chat box does.
5. **Everything stays read-only and owner-confirmed**, as `propose_job` is today.
6. **Every route is built to a cost budget** (see [Cost reduction](#cost-reduction-target-3050-lower-quality-gates-unchanged)) without using the app less: web search is about 75% of today's spend, so a cheaper search path comes first; the thesis deep-research run (up to about 15 sol calls) is expected to be the largest future cost and has its own plan section; cheap model first with escalation, slower-but-cheaper processing for work nobody waits on, and a quality gate on every change.

## Research findings

- **Agentic search often beats classic RAG on filings.** On FinanceBench an agentic keyword-search setup beat a traditional RAG pipeline by about 6 points of answer correctness ([Is Agentic RAG worth it?](https://arxiv.org/pdf/2601.07711)); coding agents moved away from vector indexes to tool-driven search for staleness and simplicity reasons ([overview](https://buzzgrewal.medium.com/ai-agents-dont-need-vector-search-anymore-inside-the-agentic-search-stack-replacing-rag-in-2026-58efcabe4f6f)). Treat these as directional, not proof for this app.
- **But retrieval quality dominates financial accuracy.** Reported FinanceBench numbers show a large gap between oracle context and basic retrieval ([summary](https://intuitionlabs.ai/articles/llm-financial-document-analysis)), and standard chunking corrupts tables. Filings need structure-aware parsing and parent/child chunks (small child chunks to match, parent section to read) ([FinSage](https://arxiv.org/pdf/2504.14493)).
- **Hybrid beats vector-only.** In Postgres, pg_trgm/tsvector plus pgvector fused with Reciprocal Rank Fusion is reported well ahead of pure vector search ([write-up](https://callsphere.ai/blog/vw7h-pg-trgm-pgvector-hybrid-retrieval-2026)). Marketing-grade numbers: validate on your own eval set. Supabase Postgres already runs here, so no new datastore.
- **Route by question, don't make everything agentic.** Plain hybrid retrieval serves most lookups; agentic loops earn their extra cost on complex questions ([adaptive routing](https://rdp.in/gpu-mart/knowledge-base/adaptive-rag-2026-hybrid-graph-agentic-tiers/)).
- **Claude platform features worth using:** programmatic tool calling lets the model write code that calls your tools and returns only aggregates, which suits "scan 40 holdings" jobs; it cannot call web search, web fetch or MCP-connector tools ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). Web fetch is a server tool ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)). Scope tool access tightly; fewer tools mean fewer mistakes ([tool-use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)).
- **Not verified:** exact current model prices/limits and whether the Claude Agent SDK or Managed Agents beat the hand-rolled loop here. Check before Phase 3 (use the `claude-api` skill).

## Architecture: four access layers

| Layer | Data | How the AI reaches it | RAG? |
| --- | --- | --- | --- |
| A. Structured | Positions, transactions, prices, fundamentals, risk, macro, ownership, insiders, graph, events, strategy, theses, verdicts | Typed, bounded, read-only tools with `source_id`, `as_of`, units | No |
| B. Prose corpus | Filings, IR releases, transcripts, news, reports, theses, owner notes | One `search_documents` tool: hybrid keyword + vector, returns passages with citation ids | Yes |
| C. The open web | Anything else | Existing web search/fetch on allowed tiers; fetched pages never mixed with private data | No (live) |
| D. Agent memory | Past runs, owner corrections, per-holding working notes | Reports, verdicts and feedback are already stored; add a small `agent_note` table the agent reads and the owner can edit | Light |

Portfolio access is layer A and is the easy part: it only needs more tools, always scoped to the question (a one-ticker question does not load the whole book).

## Agent design

- **Router first.** Cheap classification: quick lookup (one tool call, small model), chat question (tool loop), deep research (planned multi-agent run), event reaction (triggered run). Matches the profile modes in the existing plan.
- **Deep research as orchestrator + specialists.** Planner writes the brief; parallel workers each own one lens (financials and valuation, filings and events, news and web, portfolio fit and risk, counter-case); a synthesizer drafts into the typed report; the existing claim verifier gates it. Each worker's output is a `job_checkpoint`, so the resume behaviour already in `run.py` carries over. Respect the user's rule of thumb: at most 2 workers of this kind of heavy work running at once, enforced by the job budget.
- **Code owns numbers.** Valuation, risk, drift and returns stay computed in Python; the model requests them via tools and never recomputes.
- **Event-driven agents.** Triggers already exist (alerts, `free_source_alerts`, earnings checks, `monitor`). Each trigger starts a bounded run that writes an inbox item: what happened, which thesis KPI or rule it touches, evidence, proposed action. It never trades and never edits a thesis without confirmation.
- **Tool design.** Few, high-level tools (a ticker "dossier", "risk of proposed trade") beat many raw table readers. Return concise JSON; page with "more" calls.

## Cost reduction (target: 30–50% lower, quality gates unchanged)

Added 11 October 2026. Goal: the lowest AI cost that still passes the existing quality gates (claim verifier, news golden sets, earnings golden cases). Builds on [multi_provider_model_routing_plan.md](multi_provider_model_routing_plan.md), which already did three-tier routing, batch code, the `ai_result_cache`, rules-first paths and prefix-cache rules. This section lists only what that plan did **not** do, plus the cost rules the agent phases must follow so they do not multiply the bill.

**Ground rules (owner, 11 October 2026).** (1) No saving comes from using the app less: no lower step, search or token caps, no shorter answers, no dropped sections, no fewer tool rounds. Caps stay where they are or go higher; they are safety nets that normal use never reaches. (2) The owner should notice nothing except, for work that is not time-sensitive, a longer wait (batch/Flex). (3) A cheaper model, a cheaper search path or a lower reasoning effort is allowed only when a gate shows the same quality; the gate is defined before the change. Where this section earlier said otherwise, the rule above wins.

### What the spend data says (`job_step`, 27 Sep to 11 Oct 2026)

- Lifetime AI spend is **$9.65**; $7.69 of it was the 6 October backfill and switchover. Since 8 October the run rate is about **$0.15–0.50 a day (about $5–15 a month)**, all on `gpt-6-luna`, `gpt-6.1-sol` and `gemini-3.8-flash`. **No Claude spend since 8 October**, so "finish the migration" is already done.
- **Web search is about 75% of current spend.** Since 8 October: 72 searches at about $0.01 each is about $0.72 of $0.93. One `news_ai_search` run made 33 searches for $0.355, of which $0.33 was the search fee. Lifetime: 217 searches, about $2.4–3.0. Tokens on luna are almost free by comparison.
- **Output (reasoning) tokens dominate the model steps that remain.** Gap-research `research` steps on flash average 30.8K output against 16.1K input ($0.30 each; output costs 5× input). `peers` 15.4K out against 4.7K in. `news_triage` on luna wrote 53.8K output for 52.8K input. These are "judge the given evidence" tasks that should need little thinking.
- **Prefix caching barely hits:** cached input is about 9% of input on sol earnings extraction, about 11% on flash gap research, about 20% on the `news_ai_search` run. The routing plan's target is far higher.
- **Batch is barely used:** 14 of 58 luna `news_ingest` steps; every other job's `use_batch` is off.
- **Cost accounting has holes:** some Gemini steps record input tokens but zero output and `$0.000` (`news_ingest` 80K input, `ai_approvals` 8 steps with no tokens). Spend is under-reported; fix before trusting any baseline.
- **Not measured at all:** chat (no `chat` rows), standard and deep research, monthly review (one tiny row). The agent phases will make these the largest costs, so their budgets matter more than today's mix.
- Caveat: six days, one backfill, no chat. Percentages below are of the **measured mix**; the real saving is set by the C0 baseline.

### Thesis deep research (expected to be the largest cost; implemented, not yet run)

Second round, 11 October 2026, from reading `research/run.py`, `writer.py`, `web.py`, `config/research.py` and `thesis/draft.py`. No deep-thesis run exists in `job_step` yet, so every number below is an estimate until D0.

**Anatomy of one `deep-thesis` run** (profile: `gpt-6.1-sol`, effort `high`, `max_steps` 100, `max_searches` 60, `iterate`, 2 rounds, template `thesis-memo`):

1. `gather` and `read_tools` are code and stored data: no model cost. A cheap planner call (low effort) is optional.
2. **First pass: about 9 separate sol calls**, one per model-written section (`executive_summary`, `business`, `scenarios`, `catalysts`, `moat_risks`, `counter_case`, `strategy_fit`, `thesis_kpis`, `open_questions`; `financial_trend` and `valuation` are written by code). Each re-sends the whole gathered material (every source plus the code-written sentences), has the provider's web search on (about 40 of the 60 searches are split across them, 5 each), and runs at high reasoning effort. They run one after another, in template order.
3. **Up to 2 follow-up rounds**, at most 3 sections each, one more sol call per section with the whole material again, 2 searches and 3 sentences of output. About 6 more calls.
4. Claim verification (cheap model, batched) and a one-call thesis draft (2,500 output tokens): small.

So a run is up to about 15 sol calls at high effort with up to 60 searches. Three costs are hidden inside those calls: (a) the material is re-sent 15 times; (b) each search's page content is read **inside** the sol call and, per the routing plan, billed at the model's token rate, uncached, on top of the search fee; (c) high-effort reasoning output at $10 per 1M tokens, which is not the visible 12 sentences. A rough range, assuming 30–60K tokens of material and 5–10K tokens of search content per search: **about $2–6 per run**, against $0.07 for an earnings extraction. Treat as unverified; D0 measures it.

**Findings in the code that cost money without adding quality:**

- **The prompt cache is probably missing.** The writer never passes a `cache_key` (chat and the news jobs do; grep of `cache_key=` finds none in `research/`). OpenAI's `prompt_cache_key` routes related requests to the same cache; without it the 15 identical prefixes may miss, which matches the 9–20% cache-read share measured on other jobs. The writer's docstring assumes the cache works; it is not being asked to. Also keep the first part of the request byte-identical: on OpenAI the tool list comes before the system prompt and input, and the search tool's settings differ from section to section (`max_uses` is 5 for most sections, less for the last, 2 in follow-ups, 0 when the budget is spent). Whether that breaks the prefix depends on whether the provider serialises `max_uses`: verify.
- **The executive summary is written first.** It heads the template, and sections are written in template order, so it is produced before any other section exists, from raw material only. Written last, from the finished and verified sentences, it needs a few thousand input tokens instead of the whole material, and it can actually summarise the report. `thesis_kpis` and `open_questions` benefit from the same reordering. Write order and display order should be separate.
- **Search content is read by the most expensive model.** Every search the sol call makes feeds pages into a high-effort sol context. The plan already produces per-section questions with a `web_intent` and a counter-evidence intent, so the search work can be separated from the writing without changing what is searched.
- **Every section pays the same, whatever it needs.** `business` and `open_questions` run at the same model and effort as `scenarios` and `counter_case`.
- **Follow-ups pay for the whole material to get 3 sentences.**

### Rules for the agent phases (so they do not multiply cost)

- **Budget per route before building the route:** AG0 records the cost of 15 chat questions and 5 research runs on current tools (this is the unmeasured part); set per-run and monthly caps at about 2× the median, as decision 4 already says, and set a non-null `monthly_cap_usd` (it defaults to null, so nothing is capped today).
- **Chat (AG1):** luna by default with C6 escalation; `max_steps` stays at 30 (a ceiling, not a target); long histories are compacted only if a side-by-side on the chat set shows no loss, otherwise resent from the cache; tools return compact JSON with paging, as the existing tool-design rule says; one `dossier`-style tool instead of five raw readers; an answer from a rule or a cached answer never reaches the model. Tool definitions are part of the cached prefix, so keep the tool list stable and short.
- **Deep research (AG3):** the router sends a question to deep mode only when a cheaper route cannot answer it. Planner and workers run on luna/flash with low effort, the synthesizer and verifier on the cheapest model that passes the claim gate, workers share one cached company-material prefix, each worker has its own step and search cap, and at most 2 run at once (also a budget control). Workers return structured findings, not prose, so the synthesizer reads less. The deep profile keeps its `max_steps` 100 and `max_searches` 60; the saving comes from where those steps run (see "Thesis deep research" below), not from fewer of them.
- **Event agents (AG4):** a rule decides whether the model runs at all (the event touches a thesis KPI, a holding or a risk limit); triage on luna; only a confirmed material event reaches sol; non-urgent runs use batch or Flex; strictest per-run and monthly caps.
- **Retrieval (AG2):** retrieval's cost job is to shrink input (passages instead of whole filings). Embeddings are cheap (the news wire costs about $1 a month): use the Batch API (50%) for the backfill, start at 768 dimensions, embed only new document versions, store the content hash, and use no LLM reranker unless the eval proves a gain (a local cross-encoder if so).
- **Cost is a gate, not a report:** every eval (chat set, research benchmark, event replay) records cost per finished task next to accuracy; a change that raises cost per task by more than an agreed margin without a quality gain fails, the same way a quality drop does.

## Risks and controls

- **Prompt injection** from filings, news and web pages: retrieved text is data; tools and write paths are fixed by backend policy; no tool can send private data to a URL the model supplies (OWASP [prompt injection](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) and [RAG security](https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html)). Add an injected-news-article case to the evals.
- **Privacy:** portfolio and strategy are sent to the model provider on every call; keep the existing redaction (`redact.py`) and confirm the provider's data-retention terms. Embeddings add a second vendor (Google): the owner's own reports and theses are embedded there, so check Google's data-use terms and keep any portfolio-sizing detail out of embedded text where practical.
- **Cost:** agent loops multiply calls. Follow the rules in [Cost reduction](#cost-reduction-target-3050-lower-quality-gates-unchanged): per-route caps (the guard now covers every provider through `LLM`), cached stable prefixes, cheap-first cascade, batch for non-urgent runs, and cost per finished task as an eval gate. Risk of the cost work itself: a cheaper model or search path that quietly lowers quality, so every lever has a named gate.
- **Stale and wrong figures:** the claim verifier and "code owns numbers" rules from the research plan apply to every route, including the new ones.
- **Complexity:** each layer is added only if the eval shows a gain; AG2 may end with keyword-only if vectors do not help.

## Decisions (owner, 5 October 2026)

1. **Embeddings: Google Gemini embeddings (hosted).** Use **`gemini-embedding-2`** (stable, the model Google's docs recommend as newest, updated April 2026), not `gemini-embedding-001` ([docs](https://ai.google.dev/gemini-api/docs/embeddings)). It takes up to 8,192 input tokens (001: 2,048), which fits filing sections and parent chunks better; output is 3,072 dimensions by default, adjustable from 128 to 3,072 (recommended 768, 1,536 or 3,072); it is multimodal (text, image, video, audio, PDF), so filings' PDFs and charts could later be embedded directly. Differences from 001 that affect the build: the task is stated in the prompt text (for example `task: search result | query: {content}`), not through a `task_type` parameter, and the two models' vector spaces are incompatible, so never mix them in one index. The Batch API is 50% of the default embedding price, which suits the bulk backfill of filings and news. Text price was about $0.20 per 1M tokens on a third-party page ([source](https://openrouter.ai/google/gemini-embedding-2)): the docs page I read gave no price, so confirm it on Google's pricing page. Before AG2: compare 768 vs 1,536 dimensions on the eval set (storage is the only cost that scales with dimension; start at 768 unless 1,536 clearly retrieves better); confirm the paid-tier data-use terms (not verified), because tier 2 sends the owner's own reports and theses to Google. Model name and dimension are stored on each row, so a later switch means re-embedding, not a redesign. **Status 10 Oct:** the news wire already runs on `gemini-embedding-2` at 768 dimensions with a provisional $0.15 per 1M tokens in `config/budget.py` (still unchecked against Google's price page); the 768 vs 1,536 comparison and the data-use check remain open for the filings/reports corpus.
2. **Corpus: tiers 1–3.** Filings and IR releases (holdings and watchlist companies), the owner's own reports, theses and verdicts, and news. Consequences: news is the high-volume, fast-stale tier, so index only new items, keep a retention window (for example 12–24 months) for vectors while keeping full-text search over everything, and embed headline + summary, not full article bodies. Tier 4 (uploaded notes and PDFs) is out of scope for now.
3. **Proactivity: inbox only, with WhatsApp as an optional later channel.** Inbox ships in AG4. WhatsApp is an AG4 add-on, built only if the inbox proves useful. It would use Meta's WhatsApp Business Platform (Cloud API); access is free and messages are charged only outside an open 24-hour service window, where a pre-approved utility template is needed (about $0.004 per message in the US; Czech rates not checked) ([pricing overview](https://www.unipile.com/whatsapp-business-api-pricing/)). Replies inside a window are free, so a "reply to open the window" habit keeps cost near zero. Not verified: whether Meta allows a personal-use setup like this without a business account, and the exact approval steps. Check before committing; Telegram or email are fallbacks. Only events that touch a thesis KPI or a risk-limit breach would ever push.
4. **Budget: generous ceilings, enforced by the existing guard.** Principle: the owner should never be blocked in normal use, and nothing should run away unattended. Concrete shape (numbers set after AG0–AG1 from `job_step` cost data, at about 2× the median run):
   - chat and deep research: per-run caps high enough for normal use, and a shared monthly ceiling;
   - event agents (unattended): the strictest per-run and monthly caps, and they stop with "budget reached" rather than overrun;
   - at about 80% of the monthly ceiling: a visible warning; at the ceiling: `budget_guard` drops to the cheaper model instead of refusing, as it already can;
   - routing, claim verification and embeddings use the cheapest adequate model; cache stable prompt prefixes.
5. **Framework: keep the current Claude loop.** Revisit only if AG3's orchestration gets unwieldy; tools built now work under either approach.

## Decisions (delegated to the assistant by the owner, 11 October 2026)

6. **Repeat-story reuse (N5): on by default, behind its gate.** A story the novelty check marks as a repeat (similarity 0.88 or more) reuses the earlier story's stored analysis instead of a new model run. Why: a repeat carries no new facts, so the owner sees the same result, and the analysis table is already keyed by input hash. Gate before it ships: on the news golden sets, the reused analysis must match a fresh run on the fields the app shows (event type, severity, thesis links, cited spans) at the agreed margin; the 0.88 threshold is raised, never lowered, if it fails. A repeat that touches a different holding or thesis than the original is not reused.
7. **"No rush" on the manual deep-research button (D5): yes.** "Run now" stays the default and behaves exactly as today; "No rush: ready within a few hours, about half the cost" is an extra choice. Scheduled and event-triggered runs default to flex or batch. Why: it costs the owner nothing they do not choose, and the saving on the largest expected cost is about half. It ships only after one live flex or batch call per provider succeeds, with an automatic fallback to standard processing.
8. **Caps are safety nets, not savings.** No cap, step limit or token ceiling is lowered to save money anywhere in this plan (owner's rule of 11 October). Monthly caps on the news stages are set at about 2× the measured median month after the cost work, so they do not bind.
